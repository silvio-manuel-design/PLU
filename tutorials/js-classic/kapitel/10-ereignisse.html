Ereignisse & Interaktion

ERST MAL VERSTEHEN

Du sitzt am Tisch. Es klingelt an der Tür. Du stehst auf und machst auf. Du reagierst auf ein Ereignis.

Webseiten können das auch: Ein Klick ist ein Ereignis. Eine Taste ist ein Ereignis. Dein Programm sagt: „Wenn Klick — dann tu das."

Damit wird deine Seite von einem Plakat zu einem Gespräch.

WÖRTER, DIE DU JETZT LERNST

Ereignis (Event) / event

Etwas, das auf der Seite passiert: Klick, Taste, Eingabe.

Alltag: wie die Klingel an der Tür.

click

addEventListener / addEventListener

„Auf-Pass-Funktion": Meldet Code für ein Ereignis an.

Alltag: wie „Ich reagiere, sobald es klingelt."

btn.addEventListener("click", …)

Callback / callback

Eine Funktion, die später — beim Ereignis — aufgerufen wird.

Alltag: wie dein Aufstehen beim Klingeln.

function reagiere() { … }

Event-Objekt / event object

Eine Mappe mit Infos zum Ereignis: welche Taste, welches Element.

Alltag: wie der Blick durchs Guckloch.

event.target

Der erste Klick: addEventListener

Alles, was du je auf einer Website angeklickt hast, lief über Events. Jetzt baust du es selbst.

Das Grundmuster hat drei Teile: Element finden (Kapitel 09), lauschen, reagieren. Der dritte Teil ist eine Funktion — der Callback, die NICHT sofort läuft, sondern erst beim Ereignis.

Typische Fehler

Listener am falschen Element

Wenn nichts passiert, liefert querySelector vermutlich null — Selektor prüfen, bevor du den Listener verdächtigst.

„Click" statt „click"

Eventnamen sind klein geschrieben: "click", nicht "Click". Großschreibung meldet sich nie.

Callback sofort aufrufen

addEventListener("click", reagiere()) führt die Funktion SOFORT aus und meldet ihr Ergebnis an. Richtig: reagiere ohne Klammern übergeben.

Script vor dem HTML

Läuft das Script vor dem Element, findet querySelector nichts. Script mit defer im head oder ans body-Ende — siehe Kapitel 01.

Profi-Tipp

Die drei Zeilen findest du in Millionen von Webseiten — Element, lauschen, reagieren. Das ist das Fundament der Interaktion.

Eingaben lesen: input-Events und Werte

Klicks allein sind langweilig — Programme wollen WISSEN, was der Nutzer eingegeben hat.

Das input-Event feuert bei JEDER Änderung im Feld. Den Wert liest du mit element.value — und das Event-Objekt verrät dir mit event.target, welches Feld gemeint ist.

Typische Fehler

textContent statt value

Bei Eingabefeldern steht der Text in .value, nicht in textContent — das gilt für das Feld selbst.

input vs. change

input feuert bei jeder Taste, change erst nach dem Verlassen des Feldes. Für Live-Feedback: input.

event vergessen

Ohne den Parameter function (event) gibt es kein event.target — der Klassiker beim Abtippen.

Leerstring nicht prüfen

Wer „Hallo, !" ausgibt, hat den leeren Fall vergessen — kurz abfragen und einen Default setzen.

Profi-Tipp

Das Muster ‚Eingabe → Event → Ausgabe' verbindet Kapitel 02 (Werte), 09 (DOM) und 10 (Events) — du bist im Herzstück des Kurses.

DIDAKTISCHE PAUSE

Event-getriebene Programme laufen nicht von oben nach unten wie ein Buch. Sie WARTEN. Das ist anfangs strange — aber genau so funktioniert dein Handy: nichts passiert, bis etwas passiert.

Zustand und mehrere Events: Die Zähler-App

Echte Apps merken sich Dinge zwischen den Klicks. Eine Zähler-App ist das kleinste Beispiel dafür.

Die Zustandsvariable liegt AUSSERHALB der Listener — die Events ändern sie, das DOM zeigt sie. Plus- und Minus-Button teilen sich denselben Zustand.

Zähler-App

0

Der Zustand lebt in einer Variable — das DOM zeigt ihn nur an. Genau wie im Code oben.

Typische Fehler

Zustand im DOM suchen

„Lies die Anzeige, rechne +1, schreibe zurück" geht schief — die Anzeige ist keine Datenbank. Variable zählt, DOM zeigt.

Alles in einen Listener

Zwei Listener mit derselben Logik? Baue eine gemeinsame Funktion und melde sie zweimal an — nicht copy-pasten.

zaehler++ vergessen

Nur anzeige.textContent = zaehler zeigt denselben Wert immer wieder — erst das ++ ändert den Zustand.

Reset vergessen

Jede Zähler-App braucht einen Weg zurück auf 0 — beim Testen sparst du dir damit viele Klicks.

Profi-Tipp

Merksatz: Daten in Variablen, Anzeige im DOM. Nie die Anzeige als einzige Wahrheit benutzen.

Tastatur & weitere Events: Reaktionsspiel

Klicks sind nur ein Ereignistyp. Die Tastatur öffnet ein ganzes Spielfeld: Pfeiltasten, Enter, Buchstaben.

keydown feuert bei jeder Taste, event.key liefert den Tastennamen ("Enter", "ArrowLeft", …). Damit prüfst du im Callback, was passieren soll — und baust damit Spiele.

Reaktionstest

Sobald das Feld grün wird: klicken. Die Zeit messen wir in Millisekunden — Zustand + Event + Anzeige in Reinform.

Typische Fehler

keyCode statt key

event.keyCode ist alt und deprecated — nimm event.key mit dem Tastennamen.

Tastennamen falsch

"enter" funktioniert nicht — der Name ist "Enter" (case-sensitiv). Pfeiltasten: "ArrowLeft" usw.

Listener aufs falsche Element

Globale Tasten (Spielsteuerung) gehören auf document, Feld-Eingaben aufs Feld.

setTimeout vs. setInterval

setTimeout = einmal nach X ms, setInterval = immer wieder. Der Reaktionstest braucht setTimeout.

Profi-Tipp

Dein Abschlussprojekt (Highscore-Spiel) baut genau hier auf: Zustand + Events + Anzeige. Du hast alles schon.

Check: Kannst du das schon?

Zusammenfassung

  • Events = alles, was passiert; Programme warten und reagieren.
  • Element → addEventListener → Callback.
  • Eingaben per input-Event, Wert per .value.
  • Zustand in Variablen, Anzeige im DOM.
  • Tastatur-Events öffnen das Spielfeld für Spiele.
