FIRST, LET'S UNDERSTAND

You lock your front door. Not because all people are thieves — but because you don't let everyone in unchecked.

Websites are houses with many doors: input fields, URLs, forms. Security means: check the doors before anything may enter.

You don't need to be a hacker to build safely — you only need to be suspicious. Suspicion is a strength here.

The threat model: the browser doesn't trust you — trust nobody

Security starts in the head: who could do what with my inputs? Pros ask this question every time.

The client is manipulable: open DevTools, remove attributes, switch off JavaScript. Whatever the browser checks is comfort — the server must check. The chain for every input:

„Never trust, always check" applies to data from forms, from URLs and from other servers alike.

Typical mistakes

„required protects me"

HTML attributes are comfort for honest users — not protection. Every attribute is gone via DevTools.

„My students aren't hackers"

Most attacks don't come from humans at a keyboard — bots scan everything, always.

Hiding secrets in JS

Everything in the frontend is visible: API keys, passwords, internal paths NEVER belong in JavaScript.

No error assumptions

What happens when empty? When null? With a 10,000-character text? Edge cases are the real attacks.

Pro tip

First security question for every input: what's the worst thing that could stand here?

Understanding XSS: how foreign code lands on your page

XSS is the classic among web attacks — and it still works today because pages take foreign input unchecked.

The scenario (viewed defensively): a guestbook stores entries. Instead of being printed as text, the input lands as MARKUP on the page via innerHTML — and event attributes like onerror get executed. The lab shows the difference live:

XSS lab: unchecked vs. checked

innerHTML (unsafe)

textContent (safe)

On the left the input is interpreted as HTML (the bold text becomes REALLY bold), on the right as text. This is exactly the door textContent closes.

Typical mistakes

innerHTML for user input

The open door par excellence. Rule from today on: NEVER put user input into innerHTML — textContent is the default answer.

„Only my class sees the page"

Internal pages are on the network — and bots find them too. Security always applies, even on „hidden" pages.

Inventing your own sanitising

Custom regex filters are almost always leaky — later you'll use proven libraries (DOMPurify & Co.).

XSS = only <script>?

Event attributes (onerror, onclick) and URLs (javascript:) are doors too. Not just script tags.

Pro tip

Rule from today on: NEVER user input into innerHTML. textContent is your default answer.

TEACHING BREAK

First things first: don't be afraid of security. Most attacks fail against boring basic rules — exactly the ones from this chapter. Boring wins.

Validating and escaping: the tools

Suspicion is the attitude — validating and escaping are the moves.

Validating means: only allow what's permitted (whitelist, not blacklist). Escaping means: turn < > & " into harmless character sequences. Plus trim() and a length limit.

Playground

Try it right away — your own code runs here in the browser:

playground.js

Your task: add escaping for & (careful: replace it FIRST — why?).

Typical mistakes

Blacklist instead of whitelist

„Forbid <script>" forgets a thousand other doors. Whitelist: only allow permitted patterns — everything else stays out.

Escaping in only one place

Output in three places, escape in one = gap. Escape on output — then it applies everywhere.

No length limit

Unlimited input allows flooding and giant payloads — slice(0, 50) is part of it.

Validating but using the raw value

The check happened, but the raw input got stored — then even the best validation is useless.

Pro tip

Escape on OUTPUT, not on storage — your data stays raw, your display becomes safe.

Security thinking in a developer's daily life

Security is not a feature you bolt on at the end. It's a habit — with every line.

The daily rules: HTTPS always. NEVER store passwords in plain text (hash them — a server topic, but understand it). NEVER put sensitive data into frontend JS. Error messages reveal nothing. And the DevTools are your FRIEND — your tool, not the attack.

Typical mistakes

„We're too small for attacks"

Bots scan EVERYTHING automatically — being small is no protection, invisibility never was one.

Passwords in JS variables

Whatever sits in the frontend is public. Passwords belong (hashed) in the database — a backend topic.

Detailed error messages to the outside

„SQL error in line 42" helps attackers more than users — generic outside, detailed inside.

Security as a one-off topic

Whoever does security „later" never does it. Habit beats sprint — with every line.

Pro tip

You don't have to be paranoid — just consistent. Three rules are enough to start: textContent instead of innerHTML, whitelist validation, check again on the server.
