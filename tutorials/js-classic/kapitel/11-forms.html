Forms & Validation

Collect data cleanly: build forms, validate input and show friendly errors.

FIRST, LET'S UNDERSTAND

You know forms from offices and doctors: fields to fill in. If something is missing, someone tells you politely — not rudely.

Web forms are the same: fields to fill, checked on submit. And because you know JavaScript now, you build the check yourself.

WORDS YOU'RE LEARNING NOW

Building the form and its inputs

The HTML form is the frame: without a clean frame, JavaScript can't save anything.

A form bundles fields and the submit button. Every field gets a visible label — connected via for/id. The input types (text, email, number, checkbox) already give the browser hints.

Typical mistakes

Label without for/id connection

A label without for (or field not inside the label) leaves screen readers and click-on-label users stranded.

Forgetting type="email"

type="email" brings free validation and the right keyboard on mobile — pick the matching type.

Button without type

A button inside a form is automatically type="submit" — intended here, but you should know it.

Forgetting required

Required fields need required — otherwise only your JavaScript notices (or nobody).

Pro tip

Labels are mandatory — for screen readers, for everyone. A field without a label is a form with a hole.

Reading values on submit

After clicking ‚Sign up' you want the values — clean and trimmed.

The submit event fires on send-off. With event.preventDefault() you stop the page reload — then you read the values and trim them with trim().

Typical mistakes

Forgetting preventDefault

The page reloads, all input is gone — the classic. First command in the submit handler, always.

value without trim()

" Ada " with spaces breaks comparisons and storage — trim() belongs to reading.

Wrong selectors

The fields have an id, not a name — selector and markup must match.

Submitting before the listener exists

Whoever tests the form before the script runs submits it the classic way — listen first, click second.

Pro tip

event.preventDefault() is the most important one-liner of this chapter — without it your form starts over.

TEACHING BREAK

The best form in the world is the one you never notice: few fields, clear words, instant help. Every field you remove makes the form better.

Validation: HTML first, then JavaScript

HTML already checks automatically (type, required). JavaScript adds the rules HTML doesn't know.

HTML5 validation covers format and required fields (required, type, minlength, pattern). Custom rules — like „valid email" — you write as JavaScript functions.

Try it right away — your own code runs here in the browser:

playground.js

Your task: extend the check: the email should also be at least 5 characters long.

Typical mistakes

„HTML validation is enough"

Client-side checks are comfort, not protection — they can be bypassed (chapter 12!). The server must check.

Rules doubled and contradictory

HTML says one thing, JS another — users get confused. Define rules in ONE place.

Errors only via alert()

Alert chains are the unfriendliest way — errors belong at the field (step 4).

Validation scattered in the listener

Check logic belongs in small functions (like isValidEmail) — testable and reusable.

Pro tip

Rule: HTML validates the SHELL (format, required), JavaScript validates the MEANING (e.g. ‚student number starts with 2 digits').

Showing errors kindly (UX)

Everyone knows forms that shout at you. Friendly, concrete error messages are the difference between frustrated and finished users.

The message belongs AT the field (with aria-live for screen readers), the focus jumps to the first error field, and after the fix the error disappears again.

Sign-up form with live validation

Submit with an empty or wrong field: the error appears at the field and focus jumps there. Fix it → the error disappears.

Typical mistakes

All errors as an alert chain

Four alerts in a row are pure frustration — one message, at the right field.

Errors only in red

Red alone says nothing — always with text (and aria-invalid for screen readers).

Forgetting aria-invalid

Screen readers only notice the error via the attribute — set it on error, remove it on fix.

Errors never disappear

After the fix the message must go away — otherwise users think it's still wrong.

Pro tip

Test your form with the eyes of an annoyed person at 11 pm — then you know if the error messages are good.

Check: can you do this yet?

HTML first (free, instant), JS after (meaning), errors always at the field.

Summary

  • Form = frame, labels = mandatory.
  • Catch submit, preventDefault, trim values.
  • HTML checks format and required, JS checks meaning.
  • Show errors kindly at the field, set focus.
  • Client validation is comfort, not security — ch. 12 follows.

Bad prompt „Build a form."

Why is it bad?

No fields, no rules, no error display defined — the result is arbitrary.

Good prompt „Have the AI show you a form validation. Check: does it fall back to alert(), or produce clean field errors? Ask it to set aria-invalid."

Why is it good?
